# 問いの作り方
- ボタンは読者がそのまま口にする自然な疑問。「戦術理解の深化」のような編集者のテーマ名にしない。
- L1は入り口、L2は答えを読んだ後に次に湧く疑問。似た言い換えを増やさず、別の答え・別の観察行動になる場合に分ける。
- いつ何を見てこの問いが浮かぶか、答えに含める具体事項、今日見るものがどう変わるかを書く。
- 珍しい視点だけに寄せず、初めての人の基本疑問と、「分かったら気になる一歩先」を両方出す。
- 候補を出す担当では記事本文・選手全員の名鑑・サイトを作らない。人数やページ数のために同じ問いを水増ししない。
- 前提が確認できない固有の話はfact_checkに残し、「実際に起きる」と断定しない。
- 記事にしたときの文体は次の過去版ルールを想定する。
# 口調・記事の型（過去の野球ガイドから引き継ぐ）
- 読み手はサッカーをまったく知らない大人。試合前やハーフタイムにスマホで1〜2分ずつ読む。15歳くらいの人に説明するつもりで、やさしく、ただし具体性を落とさない。
- 語り手は落ち着いていて感情をあまり出さず、淡々と筋道立ててやさしく説明する。文末は「〜なのだ」「〜というわけだ」「〜だ」を基本にする。読み手には「あなた」と呼びかけてよい。すべての文を機械的に「なのだ」にそろえない。
- 数字・選手名・場面・なぜそうなるかの理屈を入れ、なんとなくでごまかさない。たとえは身近なものを使い、最後にサッカーへ戻す。キャラクター名・作品名・決めぜりふを本文に入れない。
- 専門語は初めて出すとき必ずかっこで言い換える。昔の選手・チーム・賞も一言説明。1文40字前後、1段落3文まで。箇条書きは並列の項目だけ。
- 記事は1問1ファイル。L1は500〜1000字、派生L2は250〜600字が目安。理解に必要なら長くしてよい。見出しは「ひとことで」「しくみ」「歴史・由来」（あれば）「おもしろエピソード」（条件を満たす話があれば）「今日の試合で見るなら」。今日の欄は必須で、どの選手・どの場面・どこに注目するかを具体的に書く。
- 太字は初出用語・数字・選手名に1段落1〜2か所。==黄色いマーカー==は要点に1記事3〜6か所。補足は引用形式「> 」、関連リンクはIDでつなぐ。詳細名鑑にも同じ口調と装飾を使う。
- エピソードは、誰が／どんな場面で／何をしてどうなったかがそろう話。数字・成績だけ、しくみの言い換え、直近の結果報告で埋めない。面白さは①子どもでも笑える・驚ける②今日の見え方が変わる③なぜ？が解ける、の順。下品な話や締めのダジャレは使わない。見つからなければ無理に作らない。


# 候補の出力形式
候補35〜45個を目安に、重複がない品質を優先。discovery/<担当ID>/candidates.json に次の配列を保存する：
candidate_id、question、level_hint（L1/L2）、parent_question_or_existing_id、category_hint（1〜7）、trigger（いつ何を見て思う？）、answer_scope（具体的な答えの箇条書き）、today_watch（今日何を見る？）、priority（star/normal）、novice_value（初観戦に必要な理由）、distinct_from（似た既存問との違い）、fact_check（必要な確認）、sources（手掛かりURL）。
同じフォルダのreview.mdに、候補のまとまり・欠けた視点・見送った案と理由を簡潔に書く。仮候補IDは担当文字＋連番。正式記事IDは割り当てない。
# 保存
自分のブランチsoccer/discovery-<担当ID>でカテゴリのまとまりごとにコミットし、PR・自分の差分のmainへのマージまで実行してよい。status/<担当ID>-done.mdへ完了範囲と根拠を記録。他のPRはマージせず、担当外のファイルを上書きしない。最後は件数・PR URL・不確実性だけ返す。
